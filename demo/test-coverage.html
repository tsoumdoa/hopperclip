A critical read of what the suite actually proves — not a green checkmark parade.

snapshot 2026-07-18 files left 6 ~tests ~40 prior deletion ~9 files / ~540 lines

Most of the deleted tests never failed for a real bug — they reasserted button labels, Set membership, and ternary view routing. What remains is better, but it is still not broad product coverage. The suite is concentrated on a few pure transforms (binary decode, diff, clipboard normalize) while a 900-line parser and nearly all UI behavior sit almost untested.

What is still barely tested

  • parser/src/parser.ts (~900 LOC) — core product parser. Suite only checks four option flags. Real fixtures under parser/sand/xmls/ are used elsewhere but not as a parser contract suite.
  • React UI / hooks — dialogs, paste handlers, DuckerWeb views, share flow: effectively zero automated coverage after deleting the snapshot tests (correctly — they weren’t worth it).
  • validateGhXml — exercised indirectly; no focused malformed / non-Archive / wrong-root cases of its own.
  • ghXmlToGhFile — reverse path untested.
  • Real .gh binaries from Grasshopper — native decode uses a hand-written synthetic archive, not production files.
  • node-generator / edge-generator / graph-overlay — only touched via soft flow/diff smoke.

Keep vs cut heuristic

Keep

Worth the maintenance

  • Transforms with non-obvious failure modes (binary, size caps)
  • Semantic product rules (diff overlap, ignored layout)
  • String/XML surgery that can silently corrupt archives
Cut / avoid

Usually noise here

  • SSR copy snapshots and shortcut advertising
  • One-liner helpers and object factories
  • Soft smoke: length > 0, toBeTruthy
  • Mutate-then-passthrough tests that skip real parsing

Bottom line: after pruning, the suite is honest about its job — guard a few sharp edges in GhXml/binary/diff land. It does not describe “app test coverage.” If the next addition is another expect(html).toContain(…) or a Set helper test, delete it before it lands.
