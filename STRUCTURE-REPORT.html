Hopper Clip — structure audit

Generated 2026-07-26 · src/, convex/, parser/src/ · ~17.5k lines across 140 files

The single fact that explains almost everything that feels messy: this is a Next.js App Router tree that was migrated to TanStack Start, and the old tree was never dissolved. src/routes/ is the real router. src/app/ is the fossil — it still holds every component, hook, and util in the project, still organized by Next.js route-folder conventions, still carrying page.tsx filenames and "use client" directives that do nothing here. Fix that one thing and the "hooks are half per-route, half shared" problem dissolves with it.

1. What the routes actually do

Seven real routes. TanStack file-routing: _authed and _static are pathless layouts — they wrap children without adding a URL segment, which is why /_static/privacy serves at /privacy.

3. Findings

high

① src/app/components/ and src/app/hooks/ are not shared — they're the ghcards feature

This is the exact thing you're feeling. These two folders read as "global", so anything vaguely reusable got dumped there. But the import graph says otherwise:

  • Used by exactly one feature (ghcards): add-gh-card, add-gh-dialog, add-gh-tag-display, gh-card*.tsx (9 files), gh-page-file-drop-layer, metrics-dialog, drop-overlay, and the hooks use-gh-card-control, use-validate-name-and-description, use-fetch-gh-xml, use-script-metrics, use-drop-zone.
  • Genuinely shared (2+ features): only header.tsx (4 callers), use-modifier-key-label (3), gh-flow-view.tsx (share + ghcards), and the utils gh-xml / gh-file / gzip.

So ~26 of 29 files in the "shared" folders belong to ghcards. Meanwhile src/app/ghcards/ holds only 8 view components and 2 hooks. The feature is split across two directories with the larger half in the folder named "shared" — which is why you can't tell where anything lives.

Worse, it flows backwards too: ghcards/components/gh-card-display.tsx imports components/gh-card.tsx, which imports back into ghcards/contexts/gh-cards-page-context.tsx. A cycle between the two halves of one feature.

high

② The fetch → decompress → parse → build-flow pipeline is written three times

Three hooks, three features, one pipeline — each with its own copy of the Content-Encoding: gzip headers, the size guard, the TextDecoder, and the buildGhJson → generateFlowData → setNodes/setEdges tail:

HookSource of URLDuplicated body
app/hooks/use-fetch-gh-xml.tsR2 presigned (server fn)fetch + size check + decompress + decode
app/share/hooks/use-share-flow-state.tsConvex action↑ verbatim + parse + generateFlowData
app/hooks/use-script-metrics.tsvia use-fetch-gh-xmlparse + generateFlowData + metrics

use-share-flow-state re-implements use-fetch-gh-xml's entire body rather than calling it, purely because the presigned URL comes from a different place. That's the only real difference — one URL source. It wants to be one fetchAndParseGhXml(urlPromise) function plus a thin hook.

use-fetch-gh-xml also returns a decodedRef that it never writes to — dead surface area.

medium

③ Four directories for utilities, split by no rule at all

  • src/lib/ — cn(), static-pages.ts
  • src/utils/ — bucketUrl(), generateSharableLinkUid()
  • src/app/utils/ — the 7 that actually matter (gh-xml, gh-file, gh-binary, gzip, date-format, file-drag, gh-card-edit-state)
  • src/types/ vs src/app/duckerweb/types/type.ts — and types/gh-card.ts is prop types for four specific components, which is why those components' props live 3 directories from the components themselves.

src/utils/utils.ts is the worst of it: 4 lines, named utils/utils, reads process.env.R2_URL! directly (everything else uses the validated @/env), is server-only, and is imported by both src/server/r2-storage.ts and convex/ghInternalQuery.ts — Convex reaching up into src/. It belongs in src/server/, or the Convex copy should be local.

medium

④ Dead and inert code left by the migration

  • 25 files still carry "use client" — a Next.js directive that is a no-op in TanStack Start. It reads as meaningful ("this is a client component") and isn't. Delete all 25.
  • duckerweb/components/PasteButton.tsx is dead — zero importers, unreachable from any route.
  • 5 route files are 2–9 line re-export shims (finding ①'s sibling): _static/privacy, _static/terms-of-service, _static/duckerweb, dev/flow-gallery, plus _static.tsx itself.
  • src/env.js is JavaScript in an otherwise strict-TS codebase.
  • tsconfig.tsbuildinfo (1.1 MB) and .DS_Store (18 KB) are committed; .next/ still sits in the repo root from the old framework.
medium

⑤ File naming flips convention at the duckerweb boundary

Every folder in the project is kebab-case — gh-card-display.tsx, use-tag-filters.ts, share-view.tsx — except duckerweb/components/, which is PascalCase for all 24 files (GHComponentNode.tsx, ViewControls.tsx). Both are defensible; having both is what costs you. Since kebab-case is 3:1 the majority and matches shadcn, standardize on it.

Same story for types/type.ts (singular, duckerweb) vs types/types.ts (plural, root).

low

⑥ Smaller things worth a pass

  • Fuse.js is constructed on every render in both use-filter.ts and use-validate-name-and-description.ts (no useMemo), each with its own near-identical fuseOptions literal differing only in threshold.
  • SORT_ORDERS and SortOrderZenum in types/types.ts declare the same six values twice — the file's own comment admits it: "this is not good idea...duplicating typing with zod". Derive the enum from the const array.
  • routes/index.tsx at 300 lines and the two 350–390-line legal pages are the three biggest non-feature files; the landing page's inline sub-components want their own file.
  • convex/ghCard.ts is 484 lines — the largest backend file, worth splitting by concern (posts / sharing / tags).

4. Target shape

The T3 instinct is: routes are thin, features are self-contained, and "shared" means literally used by 2+ features. Applied here that means deleting src/app/ as a concept and letting the four features stand on their own.

Order to do it in

Each step is independently shippable, and the early ones are nearly free:

#StepEffortWhy here
1Strip 25 "use client", delete PasteButton.tsx, gitignore .DS_Store / tsbuildinfo, drop .next/trivialPure deletion, zero risk, removes the loudest migration noise.
2Collapse the 5 route shims — move page.tsx bodies into their route filessmallMakes routes/ honest: one file per page. Also kills _static.tsx.
3Merge lib/ + utils/ + app/utils/ into one lib/; move bucketUrl to server/; env.js → env.tssmallMechanical, import-path-only. Removes the "which utils folder?" decision permanently.
4Move ghcards' 26 files out of app/components+app/hooks into features/gh-cards/mediumThe main event — fixes finding ①. Whatever's left behind is, by definition, genuinely shared.
5Extract one fetchAndParseGhXml(); rewrite the three hooks on top of itmediumOnly step with real logic change — do it after the moves so the diff is readable.
6Rename duckerweb's 24 PascalCase files to kebab-case; type.ts → types.tssmallNoisy diff, so do it last and alone.
7Derive SortOrderZenum from SORT_ORDERS; useMemo the two Fuse instances; split convex/ghCard.tssmallCleanup tail.

Steps 1–4 are where the "I have no idea where anything is" feeling actually goes away. 5–7 are quality, not navigability.
